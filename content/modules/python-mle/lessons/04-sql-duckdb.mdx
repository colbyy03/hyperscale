## Why an ML engineer needs SQL

Most of the data you'll train on lives in tables: warehouse exports, sensor historians, event logs, Parquet files in object storage. SQL is how every data platform lets you filter, join and aggregate those tables, and an interviewer will expect you to write it fluently.

**DuckDB** is the tool for doing that on one machine. It's an analytical SQL database that runs *inside* your Python process: no server, and nothing to install beyond a package. It stores data by column, which suits scans and aggregations over millions of rows, and it can query Parquet and CSV files, or DataFrames, directly. This course runs DuckDB in your browser, so every query below executes for real.

## Aggregates and the average-of-ratios trap

The dashboard computes `AVG(facility_kw / it_kw)`: a PUE for every 15-minute interval, then the average of those. It looks reasonable and it's wrong.

A query's clauses are written in a fixed order: `SELECT`, `FROM`, `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY`. The engine evaluates them in a different order: `FROM`, then `WHERE` (filters rows), then `GROUP BY`, then `HAVING` (filters groups), then `SELECT`, then `ORDER BY`. That's why you can't put an aggregate in `WHERE`: rows are filtered before any group exists.

## Window functions: per-row values that look at neighbours

`GROUP BY` collapses each group to one row. A **window function** computes something over a group of related rows but keeps every row. That's what you need for rolling averages, ranks, and differences from the previous reading.

```sql
AVG(temp) OVER (
  PARTITION BY rack          -- a separate window for each rack
  ORDER BY ts                -- in time order
  ROWS BETWEEN 14 PRECEDING AND CURRENT ROW  -- this row and the 14 before it
)
```

Two other patterns come up constantly with telemetry:

- **Deltas from counters.** Energy meters report a cumulative total. Per-interval energy is `kwh - LAG(kwh) OVER (PARTITION BY meter ORDER BY ts)`, plus a guard for the day the counter resets.
- **Filtering on a window result.** `WHERE` runs before windows are computed, so filter in a wrapping query or with DuckDB's `QUALIFY` clause, which plays the role of `HAVING` for windows.

## Joining sensors that don't share a clock

Real sensors don't report in sync. The inlet sensors log on the minute; the power meter reports when it feels like it. An equality join on timestamps matches almost nothing. You want, for each minute, *the most recent reading at or before it*: an **as-of join**. In pandas that's `merge_asof`; in DuckDB it's `ASOF JOIN`.

<Craft title="Telemetry SQL habits">
- Decide the time semantics first. Is a reading an instant, or an average over the interval before it? Are timestamps in UTC? Daylight-saving shifts duplicate or skip an hour of local time, a classic source of double-counted energy.
- Prefer ratios of sums for any "per" metric over a period, and say so in the column name (`pue_energy_weighted`).
- Count rows before and after every join. A join that silently multiplies or drops rows is the most common bug in feature pipelines.
- DuckDB reads Parquet in place (`SELECT … FROM 'meters/*.parquet'`) and only loads the columns and row groups a query needs. Columnar files and filters on partition columns keep big scans cheap.
</Craft>
